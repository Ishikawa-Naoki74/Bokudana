# /project:refactor-clerk

認証ライブラリに関連するコードを、**現在インストールされているバージョンと構成のベストプラクティス**に従って、セキュリティと保守性の観点からリファクタリングする。

## ステップ 0：プロジェクト構成の自動検出（必須）

リファクタリングを開始する前に、必ず以下を実行してプロジェクトの実際の構成を把握する。

```bash
cat package.json
```

### 0-1. 認証ライブラリの検出

`package.json` の `dependencies` を確認し、使用している認証ライブラリを特定する。

| 検出するパッケージ | 参照すべき公式ドキュメント |
|---|---|
| `@clerk/expo` | https://clerk.com/docs/quickstarts/expo |
| `@clerk/nextjs` | https://clerk.com/docs/quickstarts/nextjs |
| `@clerk/clerk-react` | https://clerk.com/docs/quickstarts/react |
| `next-auth` / `@auth/core` 等 | https://authjs.dev/getting-started |
| `firebase` (Auth) | https://firebase.google.com/docs/auth |
| `@auth0/auth0-react` 等 | https://auth0.com/docs/quickstart/spa/react |
| `supabase` | https://supabase.com/docs/guides/auth |
| 上記以外 | package.json に記載のバージョンの公式ドキュメントを参照 |

> ⚠️ 認証ライブラリが複数検出された場合は、エントリポイント（`app/_layout.tsx` / `_app.tsx` / `main.tsx` 等）を確認して実際に使われているものを特定すること。

### 0-2. フレームワーク（ルーティング）の検出

認証フロー（ログイン後リダイレクト・未認証ガード等）の実装方法はルーティングライブラリに依存するため、併せて確認する。

| 検出するパッケージ | 認証フローの実装方針 |
|---|---|
| `expo-router` | `app/(auth)/` グループでのルート分離 → https://docs.expo.dev/router/introduction/ |
| `@react-navigation/native` | Navigator内でのスタック分岐 → https://reactnavigation.org/docs/auth-flow |
| `next` | `middleware.ts` + `app/` ディレクトリでのルート保護 → 各認証ライブラリのNext.js向けガイドを参照 |
| 上記以外 | 検出したライブラリのドキュメントから認証フロー実装例を参照 |

### 0-3. Convex連携の検出

`package.json` に `convex` が含まれる場合、認証とConvexの連携ドキュメントも確認する。

| 組み合わせ | 参照すべきドキュメント |
|---|---|
| Clerk + Convex | https://docs.convex.dev/auth/clerk |
| Auth.js + Convex | https://docs.convex.dev/auth/nextauth |
| Firebase Auth + Convex | https://docs.convex.dev/auth/firebase |
| Auth0 + Convex | https://docs.convex.dev/auth/auth0 |
| Convex なし | Convex連携の項目はスキップする |

### 0-4. Changelogの確認

検出した認証ライブラリの Changelog を確認し、破壊的変更・非推奨APIがないかチェックする。
（各ライブラリの GitHub Releases または公式 Changelog ページを参照）

## 対象ファイル

`$ARGUMENTS` にファイルパスが指定された場合はそのファイルを対象にする。指定がない場合は以下を自動スキャンする：
- エントリポイント（`app/_layout.tsx` / `_app.tsx` / `main.tsx` 等）
- 認証関連画面（sign-in, sign-up, onboarding 等のファイル名を含むもの）
- `components/` 配下の認証関連コンポーネント
- `hooks/` 配下の認証フック
- `convex/` 配下の認証ヘルパー（Convexを使用している場合）

### ファイル数の確認と分割実行

スキャン前に対象ファイル数を確認する：

```bash
find . -name "*.ts" -o -name "*.tsx" 2>/dev/null \
  | grep -v node_modules | grep -v _generated \
  | xargs grep -l "auth\|Auth\|sign-in\|signIn\|login\|Login\|clerk\|Clerk" 2>/dev/null \
  | wc -l
```

**ファイル数に応じて以下の方針で対応する：**

| ファイル数 | 対応方針 |
|---|---|
| 〜10ファイル | 一括処理してよい |
| 11〜25ファイル | 層単位（Provider → フック → 画面 → バックエンド）で分割して処理する |
| 26ファイル以上 | 必ず分割する。一括処理を試みてはならない |

**26ファイル以上の場合は、実行前に以下を提示してユーザーに確認を求める：**

```
⚠️ 認証関連ファイルが多いため、分割して実行することを推奨します。

推奨する実行順序：
1. /project:refactor-clerk convex/lib/（認証ヘルパーを先に確定する）
2. /project:refactor-clerk hooks/（カスタムフックを整理する）
3. /project:refactor-clerk app/（画面・レイアウトを整理する）
4. /project:refactor-clerk components/（UIコンポーネントを整理する）

一括実行しますか？それとも上記の順で分割実行しますか？
```

## リファクタリング方針（原則ベース）

以下は**ライブラリ・バージョンに依存しない原則**である。具体的なAPIは、ステップ0で検出したライブラリの公式ドキュメントに従うこと。

### 1. Provider設定の原則
- 認証Providerはアプリのエントリポイントで一度だけ設定する
- 認証キー・シークレットは環境変数から取得し、コードにハードコードしない
- トークンはプラットフォームの安全なストレージに保持する（各ライブラリの推奨方法に従う）
- バックエンド（Convex等）との連携は、**ステップ0で確認した連携ドキュメント**に従った方法で一元管理する

### 2. 認証フローの原則
- **ステップ0で検出したルーティングライブラリ**の推奨パターンで認証済み画面と未認証画面を分離する
- 未認証ユーザーのリダイレクトロジックをエントリポイントに集約する
- 各認証方式（OAuth・メール・電話番号等）のエラーハンドリングを統一する
- ユーザーへのエラーメッセージはわかりやすい表現に統一する

### 3. フック・API利用の原則
- **検出した認証ライブラリ**が提供するフック・クラスの責務を公式ドキュメントに従って明確に使い分ける
- 認証チェックのロジックをカスタムフックに抽出して再利用する
- ローディング状態のハンドリングを全箇所で統一する
- 認証オブジェクトが `null` になりうることを考慮した安全なアクセスを行う

### 4. バックエンド連携の原則（Convex使用時）
- バックエンドのサーバー関数内でユーザー検証を行うヘルパーを共通化する
- クライアント側の認証チェックのみに依存せず、必ずサーバー側でも検証する
- ユーザー検索に使うフィールドのインデックスがスキーマに定義されていることを確認する
- ユーザーIDの管理方法をプロジェクト全体で統一する

### 5. セキュリティの原則
- センシティブな操作（アカウント削除・決済等）には適切な認証強度を設ける
- トークンの有効期限切れを適切にハンドリングし、自動リフレッシュを確認する
- ユーザーIDは一貫した方法で管理し、複数の識別子を混在させない

### 6. UI/UXの原則
- 認証状態のローディング中は統一されたフィードバックを表示する
- 認証エラーはユーザーが次のアクションを取れるよう適切に表示する
- 認証フォームのキーボード表示時にUIが崩れないよう対応する
- パスワードリセット・認証再送など主要なフォールバックを実装する

## 禁止事項
- ステップ0の構成検出・ドキュメント参照をスキップしない
- 検出された認証ライブラリ以外のAPIを混入させない
- 認証キー・シークレットをコードにハードコードしない
- クライアント側の認証チェックのみでサーバー側の検証を省略しない
- 認証フローの変更によって既存ユーザーがログアウトされる変更を行わない
- 前バージョンのAPIを「おそらく動くだろう」という推測で使用しない
