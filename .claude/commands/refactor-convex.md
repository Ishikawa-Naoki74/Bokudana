# /project:refactor-convex

Convex のバックエンドコード（クエリ・ミューテーション・アクション・スキーマ）を、**現在インストールされているバージョンと構成のベストプラクティス**に従って徹底的にリファクタリングする。

## ステップ 0：プロジェクト構成の自動検出（必須）

リファクタリングを開始する前に、必ず以下を実行してプロジェクトの実際の構成を把握する。

```bash
cat package.json
ls convex/
cat convex/schema.ts 2>/dev/null || echo "schema.ts が存在しません"
```

### 0-1. Convexバージョンの確認

`package.json` から `convex` のバージョンを取得し、以下を参照する。

| 確認先 | URL |
|---|---|
| 公式ドキュメント | https://docs.convex.dev/ |
| Changelog | https://news.convex.dev/ |
| TypeScript API リファレンス | https://docs.convex.dev/api/ |

> ⚠️ Convexはアップデートが活発なため、スキーマ定義・クエリAPI・認証APIが変わっている可能性がある。必ずドキュメントを確認してから書き直すこと。

### 0-2. 認証ライブラリとの連携方式の検出

`package.json` の `dependencies` を確認し、使用している認証ライブラリを特定する。

| 検出するパッケージ | 参照すべき連携ドキュメント |
|---|---|
| `@clerk/expo` / `@clerk/nextjs` 等 | https://docs.convex.dev/auth/clerk |
| `next-auth` / `@auth/core` 等 | https://docs.convex.dev/auth/nextauth |
| `firebase` / `firebase-admin` 等 | https://docs.convex.dev/auth/firebase |
| `@auth0/auth0-react` 等 | https://docs.convex.dev/auth/auth0 |
| 認証ライブラリなし / カスタム実装 | https://docs.convex.dev/auth/custom-auth |

> ⚠️ 認証ライブラリが複数検出された場合は、実際にConvexのProviderと連携しているものを `app/` や `_layout.tsx` のエントリポイントから確認して判断すること。

### 0-3. Convexディレクトリ構成の把握

`ls convex/` の結果から以下を確認する：
- `schema.ts` の有無（なければスキーマ未定義のプロジェクト）
- 自動生成ディレクトリの名前（`_generated/` など）→ **このディレクトリは編集しない**
- 既存ファイルの命名規則（機能別 / レイヤー別 など）

## 対象ファイル

`$ARGUMENTS` にファイルパスが指定された場合はそのファイルを対象にする。指定がない場合は以下を自動スキャンする：
- `convex/` ディレクトリ配下の全 `.ts`（ステップ0で確認した自動生成ディレクトリは除外）

### ファイル数の確認と分割実行

スキャン前に対象ファイル数を確認する：

```bash
find convex -name "*.ts" ! -path "*/\_generated/*" 2>/dev/null | wc -l
```

**ファイル数に応じて以下の方針で対応する：**

| ファイル数 | 対応方針 |
|---|---|
| 〜15ファイル | 一括処理してよい |
| 16〜30ファイル | 機能単位で分割して順番に処理する |
| 31ファイル以上 | 必ず分割する。一括処理を試みてはならない |

**31ファイル以上の場合は、実行前に以下を提示してユーザーに確認を求める：**

```
⚠️ 対象ファイルが多いため、分割して実行することを推奨します。

推奨する実行順序：
1. /project:refactor-convex convex/schema.ts（スキーマを先に確定する）
2. /project:refactor-convex convex/lib/（共通ヘルパーを先に整理する）
3. /project:refactor-convex convex/（機能ファイルを機能単位で順番に）

一括実行しますか？それとも上記の順で分割実行しますか？
```

## リファクタリング方針（原則ベース）

以下は**ライブラリ・バージョンに依存しない原則**である。具体的なAPIは、ステップ0で確認した公式ドキュメントに従うこと。

### 1. スキーマ設計の原則
- すべてのテーブルを明示的に型定義する
- フィールド名の命名規則を統一する（現バージョン推奨の規則に従う）
- 頻繁なクエリパターンに合わせてインデックスを定義する
- 任意フィールドと必須フィールドを明確に区別する
- テーブル間の参照は型安全な方法で定義する

### 2. データ取得（クエリ）の原則
- 読み取り専用操作と書き込み操作を明確に分離する
- N+1クエリを避け、インデックスを活用した効率的な取得を行う
- 認証が必要な操作は必ずユーザー検証を先頭で行う
- 外部から呼ばれない内部ロジックは内部関数として定義する
- 返却型を明示的に定義し、暗黙の `any` を排除する

### 3. データ更新（ミューテーション）の原則
- 書き込み操作と読み取り操作を適切な関数型で分離する
- 引数のバリデーションはConvexのバリデーション機構を活用する
- トランザクションの一貫性を意識し、関連する書き込みをまとめる
- クライアントの楽観的更新を考慮した返却値を設計する

### 4. 外部連携（アクション）の原則
- 外部API呼び出しや副作用を伴う処理をアクションに集約する
- アクション内でのDB操作は直接行わず、ミューテーション経由で行う
- 冪等性を意識した設計にする
- 長時間処理はConvexのスケジューリング機能を活用する

### 5. 認証連携の原則
- **ステップ0で検出した認証ライブラリ**の連携ドキュメントに従ったユーザー検証を実装する
- ユーザー検証ロジックは共通ヘルパーとして一元化する（認証ライブラリが変わっても差し替えやすい形にする）
- すべての公開エンドポイントでユーザー認証を検証する
- 他ユーザーのデータへの不正アクセスを防ぐ所有権チェックを実装する

### 6. コードの整理原則
- 複数の関数で共通するロジックはヘルパー関数に抽出する
- 型定義は共通ファイルにまとめる
- ファイルは機能単位で分割し、1ファイルに複数の責務を持たせない
- 内部専用ロジックは外部から呼び出せない形式で定義する

## 出力フォーマット

```
## ✅ Convex リファクタリング完了

### 検出した構成
- convex: x.x.x
- 連携している認証ライブラリ: （検出したパッケージ名とバージョン）

### 変更ファイル
- convex/〇〇.ts：変更内容の1行サマリー

### 主な改善点
- （箇条書きで3〜5点）

### スキーマ変更（提案）
- （スキーマに変更提案がある場合のみ記載・自動適用しない）

### 注意点・TODO
- （残課題があれば記載）
```

## 禁止事項
- ステップ0の構成検出・ドキュメント参照をスキップしない
- 検出された認証ライブラリ以外の認証パターンを混入させない
- スキーマ変更を伴うマイグレーションを自動実行しない（変更案を提示するにとどめる）
- 既存のAPIインターフェース（関数名・引数）を変更しない
- Convexが自動生成するファイルを編集しない
- 前バージョンのAPIを「おそらく動くだろう」という推測で使用しない
